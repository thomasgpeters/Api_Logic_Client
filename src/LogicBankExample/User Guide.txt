# LogicBank for FutureBasic
Business rules for your data, declared once and enforced on every save. You tell it what must be true (an order's total is the sum of its items, say, or a customer's balance never goes over the credit limit) and LogicBank for FutureBasic keeps it true, however the data changes and in whatever order.

## Why "LogicBank"?
**Logic** is your business logic: the rules of your business, the things that must always be true about your data. LogicBank looks after them here, in one place, so they aren't scattered through your windows and buttons.
**Bank** is like your own bank. You trust it to keep what you put in safe and exact, and to give it back when you ask. You also never have to work out your own balance, interest or charges, because the bank does that arithmetic for you on every transaction, by its rules. LogicBank does the same for your data. You put your records in, its rules keep every total, balance and limit correct on every save, and whatever you take out is right.

It's a free, open-source module (MIT). We were inspired by LogicBank for API Logic Server and rewrote it for FutureBasic. This example shows it at work on three objects kept in memory: Customer, Order and Item.

## How it fits together
- **Your rules** (Rules.incl): one DeclareRules function that declares every rule. Formulas and constraints are small FB functions, while sums, counts, copies, parent checks and delete actions are declared by name.
- **The engine** (Logic Rules.incl, Logic Row.incl, Logic Engine.incl): checks the rules against the model when they are activated, orders the formulas, and runs the right rules on every save.
- **The model** (Data Model.incl and the resource Model.json): the entities, their fields and keys, and the relationships between them, such as which Order belongs to which Customer.
- **The data layer**: Data Memory.incl keeps the objects in memory (as this example does), and Data Records.incl keeps them in SQLite, through the SQL Generator. The engine is the same either way.

## Saving through the rules
You never write a record yourself. You hand it to the engine, which runs the rules and saves it, or refuses and puts everything back as it was.
```
CFMutableDictionaryRef item = fn MutableDictionaryNew
MutableDictionarySetObjectForKey( item, fn NumberWithLong( 1 ), @"OrderId" )
MutableDictionarySetObjectForKey( item, @"Widget", @"Product" )
MutableDictionarySetObjectForKey( item, fn NumberWithDouble( 2 ), @"Quantity" )
MutableDictionarySetObjectForKey( item, fn NumberWithDouble( 100 ), @"UnitPrice" )
if ( fn LogicInsert( @"Item", item ) == NO ) then alert 1, NSAlertStyleWarning, @"Not saved", fn LogicMessage, @[@"OK"], NO
```
- **LogicInsert( entity, record )**: inserts the record, and sets a generated key in it.
- **LogicUpdate( entity, record, NULL )**: the record holds the key and the fields that change; the others keep their values.
- **LogicDelete( entity, keyValues )**: deletes the record, with its delete actions.
- **LogicMessage**: why the last save was refused, ready to show the person using your app.
One save is one transaction. When any rule refuses, whether here or in a parent the save changed, every change the save made is rolled back.

## The rules, one kind at a time

## Formula: a value worked out from the row
An Item's amount is its quantity times its price, less the order's discount. The function reads the row and returns the value. The last argument lists what it depends on, so the engine recomputes it only when one of those changes. "Order.Discount" is a field of the parent, so when the order's discount changes, every item of the order is recomputed.
```
local fn ItemAmount( logicRow as LogicRowRef ) as CFTypeRef
double amount = fn LogicDouble( logicRow, @"Quantity" ) * fn LogicDouble( logicRow, @"UnitPrice" ) * ( 100.0 - fn LogicParentDouble( logicRow, @"Order", @"Discount" ) ) / 100.0
end fn = fn NumberWithDouble( fix( amount * 100.0 + 0.5 ) / 100.0 )

fn LogicFormula( @"Item", @"Amount", @fn ItemAmount, @[ @"Quantity", @"UnitPrice", @"OrderId", @"Order.Discount" ] )
```

## Sum and count: a parent adds up its children
An Order's total is the sum of its items' amounts, and its item count is how many there are. Nothing is added up again from scratch. When one item changes, the engine adjusts the order by the difference and saves the order through its own rules, which in turn adjust the customer.
```
fn LogicSum( @"Order", @"AmountTotal", @"ItemList", @"Amount", NULL )
fn LogicCount( @"Order", @"ItemCount", @"ItemList", NULL )
```
A **where** function counts only some children. A customer's balance is the total of its orders not yet shipped, so shipping an order takes it out of the balance straight away.
```
local fn OrderUnshipped( logicRow as LogicRowRef ) as BOOL
end fn = fn LogicIsEmpty( logicRow, @"ShippedDate" )

fn LogicSum( @"Customer", @"Balance", @"OrderList", @"AmountTotal", @fn OrderUnshipped )
fn LogicCount( @"Customer", @"UnshippedOrders", @"OrderList", @fn OrderUnshipped )
```

## Constraint: what must always be true
A constraint is a function that answers YES when all is well. When it answers NO, the save is refused with the message (where {Name} and {Balance} are filled in from the row) and everything rolls back. A constraint on a parent looks after every child too, so adding an item to an order can be refused because the customer's balance would go over the limit.
```
local fn CustomerWithinCredit( logicRow as LogicRowRef ) as BOOL
end fn = ( fn LogicDouble( logicRow, @"Balance" ) <= fn LogicDouble( logicRow, @"CreditLimit" ) )

fn LogicConstraint( @"Customer", @fn CustomerWithinCredit, @"{Name}'s balance {Balance} would exceed the credit limit {CreditLimit}" )
```

## Copy: a parent's value, kept as it was
An order copies the customer's discount when it's placed. A copy doesn't follow later changes the way a formula does, so when Alice's discount goes up, her earlier order keeps the discount it was placed with. (The copy is made again if the row moves to another parent.)
```
fn LogicCopy( @"Order", @"Discount", @"Customer", @"Discount" )
```

## Parent check: the parent must exist
```
fn LogicParentCheck( @"Order", @"Customer", @"There is no customer {CustomerId}" )
```

## Delete actions: what happens to the children
- **prevent**: the parent cannot be deleted while it has children.
- **cascade**: deleting the parent deletes its children, each through its own rules (so the totals above them come down).
- **nullify**: the children stay, without the parent.
```
fn LogicDeleteAction( @"Customer", @"OrderList", @"prevent", @"{Name} still has orders" )
fn LogicDeleteAction( @"Order", @"ItemList", @"cascade", NULL )
```

## Events: your own code at a save
A row event runs during the save, and can set values. A commit event runs once the save has been kept, which is the place to send a message, write a log or refresh a window.
```
fn LogicRowEvent( @"Order", @fn OrderSaving )
fn LogicCommitEvent( @"Order", @fn OrderSaved )
```

## What a rule reads (Logic Row.incl)
- **LogicDouble( logicRow, field )**, **LogicLong**, **LogicString**, **LogicValue**: the row's field.
- **LogicIsEmpty( logicRow, field )**: the field is empty.
- **LogicOldValue( logicRow, field )**, **LogicChanged( logicRow, field )**: the value before this save, and whether it changes.
- **LogicIsInsert / LogicIsUpdate / LogicIsDelete( logicRow )**: what the save is.
- **LogicParentDouble( logicRow, role, field )**, **LogicParentString**, **LogicParentValue**: a field of the parent (role: "Order", "Customer").

## Activating the rules
Declare the rules, then activate them once, when the app starts. Activation checks every name against the model (entities, fields, child lists, parent roles) and puts the formulas in order. If a rule doesn't fit the model, it's reported in the NSLog window, and no save runs until it's fixed.
```
fn DeclareRules
if ( fn LogicActivate == NO ) then alert 1, NSAlertStyleWarning, @"The rules could not be activated.", @"See the NSLog window.", @[@"OK"], NO
```
Logging is off by default. Every NSLog is gated on isLoggingOn, a global in the app's own globals file, which starts out as NO. Story > Log to NSLog turns it on, and the engine then writes every rule it runs to the NSLog window, indented as one save leads to the next. The story is written there too. In your own app, set isLoggingOn = YES in your globals while you develop.

## The model: Model.json
The model names each entity's fields and keys and its relationships. The child has the parent role (toone: "Customer"), the parent has the child list (tomany: "OrderList"), and both name the fields that link them.
```
{ "name": "Order", "keys": [ "Id" ], "keyKind": "autoincrement",
  "fields": [ { "name": "Id" }, { "name": "CustomerId" }, { "name": "ShippedDate" }, ... ],
  "relationships": [
    { "name": "Customer", "direction": "toone", "resource": "Customer", "fks": [ "CustomerId" ], "parentKeys": [ "Id" ] },
    { "name": "ItemList", "direction": "tomany", "resource": "Item", "fks": [ "OrderId" ], "parentKeys": [ "Id" ] } ] }
```

## Using LogicBank for FutureBasic in your own app
All you need is the plain FutureBasic editor:
- Drag the module's files into your project, in this order: Data Model.incl; Data Memory.incl (or, for SQLite: Data SQLite.incl, the SQL Generator's DataObject files, and Data Records.incl); Logic Rules.incl; Logic Row.incl; Logic Engine.incl.
- Add your Model.json to the project's resources (for SQLite, set "database" to the file's path).
- Write your Rules.incl after them, and call DeclareRules and LogicActivate when the app starts.
- Save with LogicInsert, LogicUpdate and LogicDelete, and show LogicMessage when a save is refused.
- For SQLite, add -lsqlite3 to the Build Settings' compiler options.

## Writing rules by hand, or with App Builder
With the module on its own, you write the rules in FB, as above, and test them yourself. If you'd like help, **App Builder for FutureBasic** writes them for you from sentences in your model's own names, such as "an order's total is the sum of its items' amounts". It checks them against the model, tests every rule with scenarios, and builds the whole app around them, with its windows, lists, forms and data binding. You'll find more on Imagery's FutureBasic page (About Imagery Business Systems, in the application menu).
