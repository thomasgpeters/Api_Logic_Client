# Logic for FutureBasic — Engine and Studio (design)

*Status: design. Nothing built yet. Phase: after the lite shell (navigator + List + Form
over SQLite) works, since rules need a data layer to run against.*

Business logic declared as rules and enforced on every save, the way
[LogicBank](https://github.com/valhuber/LogicBank) (Val Huber) does it for API Logic
Server. Here **the rules are FutureBasic code**, the engine is a FutureBasic runtime file,
and the rules are authored in a **Logic Studio built into Api Logic Client**.

Two parts:

| Part | Where | What |
|---|---|---|
| **Logic Engine** | `src/Runtime/Logic Engine.incl` (copied into every generated app) | Runs the rules on insert / update / delete, inside the app's SQLite transaction |
| **Logic Studio** | a Rules page in the generator (Imagery Logic Studio) | Author rules per entity against the model; saved in the project; generates the rule code |

---

## 1. What LogicBank does (studied from the Python source, 2026-11-16)

LogicBank hooks SQLAlchemy's `before_flush`. For each changed row it builds a
`LogicRow` (row + old row + insert/update/delete) and runs a fixed sequence. Rules are
*declared*, never called; the engine decides when.

**Rule types**

| Rule | Example (Northwind) | Meaning |
|---|---|---|
| `sum` | `Customer.Balance = sum(Order.AmountTotal where ShippedDate is None)` | parent attribute = sum of child attribute (optionally filtered) |
| `count` | `Customer.UnpaidOrderCount = count(Order where …)` | parent attribute = number of qualifying children |
| `formula` | `OrderDetail.Amount = Quantity * UnitPrice` | attribute computed from the row (and its parents) |
| `copy` | `OrderDetail.UnitPrice = copy(Product.UnitPrice)` | value copied from the parent **on insert**, then independent |
| `constraint` | `Customer.Balance <= CreditLimit`, else "balance exceeds credit" | condition that must hold; failure rolls back the transaction |
| `commit_constraint` | as above, checked once at commit | for conditions that depend on aggregates finishing |
| `parent_check` | an Order must have a Customer | referential integrity |
| `row_event`, `early_row_event`, `commit_row_event`, `after_flush_row_event` | send mail when an order ships | code run at a defined point |
| `allocate`, `copy_row`, `copy_children` (extensions) | allocate a payment across unpaid orders; clone an order | multi-row patterns |

**Per-row sequence** (`logic_row.py`):

| Insert | Update | Delete |
|---|---|---|
| early events | early events | early events |
| defaults (aggregates start at 0) | check parents (re-parenting) | |
| load parents | | |
| copy rules | copy rules | |
| formulas, in dependency order | formulas — **pruned** when nothing they read changed | |
| adjust parent aggregates | adjust parent aggregates | adjust parent aggregates |
| constraints | constraints | cascade delete / nullify / prevent |
| row events | cascade changed attributes to children; row events | row events |

Then at commit: commit constraints, commit row events.

**The ideas that matter**

1. **Adjustment, not re-aggregation.** A sum is never recomputed with `SELECT SUM`; the
   parent is adjusted by the *delta*: inserted child +value, deleted child −value,
   updated child +(new − old), and where-clause transitions (now qualifies: +new; no
   longer: −old). Re-parenting (child moved to another parent) adjusts both parents.
2. **One parent update per role.** All aggregates along one child→parent role adjust the
   same parent row, which is saved once (`ParentRoleAdjuster`).
3. **Chaining.** Saving the adjusted parent runs *its* logic (its formulas, its
   constraints, its own parent's aggregates): `OrderDetail.Amount` → `Order.AmountTotal`
   → `Customer.Balance` → constraint `Balance <= CreditLimit`. Changing a parent attribute
   that children `copy` or reference cascades down the same way.
4. **Dependencies from the rule text.** Formula dependencies are found by scanning the
   rule's source for `row.<Attr>` (and `row.<Role>.<Attr>` for parent references); formulas
   run in an order computed from them (cycle → error at start-up), and are skipped when no
   dependency changed.
5. **Old values.** Every rule sees the row and the old row.

## 2. The FutureBasic edition

### Rules are FB code

A rule set is FB source, one file per entity, generated by the Studio and readable (and
editable) by hand:

```
// Order Rules.incl  -  generated by Logic Studio; edit in the Studio

// Order.AmountTotal = sum( OrderDetail.Amount )
fn LogicSum( @"Order", @"AmountTotal", @"OrderDetail", @"Amount", @"OrderDetailList", NULL )

// Customer.Balance = sum( Order.AmountTotal where ShippedDate is empty )
fn LogicSum( @"Customer", @"Balance", @"Order", @"AmountTotal", @"OrderList", @fn OrderIsUnshipped )

// OrderDetail.UnitPrice = copy( Product.UnitPrice )
fn LogicCopy( @"OrderDetail", @"UnitPrice", @"Product", @"UnitPrice" )

// OrderDetail.Amount = Quantity * UnitPrice
local fn OrderDetailAmount( row as LogicRowRef ) as CFTypeRef
end fn = fn NumberWithDouble( fn LogicDouble( row, @"Quantity" ) * fn LogicDouble( row, @"UnitPrice" ) )
fn LogicFormula( @"OrderDetail", @"Amount", @fn OrderDetailAmount, @[ @"Quantity", @"UnitPrice" ] )

// Customer: Balance <= CreditLimit
local fn CustomerCreditCheck( row as LogicRowRef ) as BOOL
end fn = ( fn LogicDouble( row, @"Balance" ) <= fn LogicDouble( row, @"CreditLimit" ) )
fn LogicConstraint( @"Customer", @fn CustomerCreditCheck, @"Balance %@ exceeds credit %@", @[ @"Balance", @"CreditLimit" ] )
```

- **Declarative rules** (`sum`, `count`, `copy`) are one registration line; the engine
  does the work.
- **Formulas, constraints, where-conditions and events are FB functions** taking a
  `LogicRowRef` and returning a value / BOOL. They are registered by address (`@fn`) and
  called by the engine through a one-line `cln` cast to a C function pointer — the
  convention FB uses for `@fn` callbacks to Cocoa (`def fn … using` also exists, but needs a
  global pointer per call site, unsafe when saves chain).
- **Dependencies are explicit** (`@[ @"Quantity", @"UnitPrice" ]`). The Studio fills them
  in by scanning the function body for `fn LogicValue/LogicDouble/… ( row, @"X" )` — the
  same trick as LogicBank's `row.X` scan, but done once at generation time, so the
  engine needs no source parsing.
- Row access goes through the engine (`LogicValue`, `LogicDouble`, `LogicOldValue`,
  `LogicParent( row, @"Customer" )`), never straight SQL: that is how the engine knows
  what changed and what to chain.

### Engine (`Logic Engine.incl`, runtime)

- **Hook point:** the generated data layer's save path. The shell's Save / Delete call
  `LogicSave( entity, record, old )` / `LogicDelete( entity, record )` instead of the raw
  `ExecuteInsert/Update/Delete`; the engine wraps everything in one SQLite transaction
  (`BEGIN … COMMIT`, `ROLLBACK` on a failed constraint) and does the writes itself.
- **Rule bank:** a dictionary built once at start-up by the `… Rules.incl` registrations:
  `entity → { formulas (sorted by dependencies), copies, constraints, events,
  aggregates by child role }`. Cycle in formulas → alert at start-up, naming them.
- **LogicRow:** a dictionary `{ entity, row, old, verb, nest }` (`LogicRowRef`).
- **Per-row sequence:** as in §1, same order.
- **Aggregates:** delta adjustment and where-transitions exactly as in §1; one parent
  read + one parent write per role; the parent write recurses through `LogicSave` (chaining),
  with a nesting limit as a safety net.
- **Constraint failure:** rollback, and the message (with `%@` values) goes back to the
  Form, shown next to the Save button (later: a toast).
- **Log:** gated on `isLoggingOn`, indented by nesting level, like LogicBank's logic log —
  it is how a developer sees *why* a value changed.
- **Model knowledge** (keys, relationships, roles) comes from `Model.json`, which already
  carries them from the SQLite model.

### Where the rules come from

1. **Authored in the Studio** (below).
2. **Imported from an ALS project** — `logic/declare_logic.py` uses the same rule
   vocabulary; sum/count/copy/constraint lines with simple lambdas translate one-to-one,
   anything else is brought in as a commented stub to rewrite in FB.
3. **Hand-written** in the `… Rules.incl` files (the Studio reads back only what it
   generated; hand edits outside its markers are kept).

## 3. Logic Studio (Imagery Logic Studio), in the generator

A **Rules** page beside the entity definitions (Model menu → *Rules…*, and a tab on the
entity page):

```
+--------------+-----------------------------------------------------------+
| Entities     | Customer — Rules                                    [+ ▾] |
|  Category    |-----------------------------------------------------------|
|  Customer  ◀ | Σ  Balance = sum( Order.AmountTotal where unshipped )     |
|  Order       | #  UnpaidOrderCount = count( Order where unshipped )      |
|  OrderDetail | ✓  Balance <= CreditLimit  "Balance exceeds credit"       |
|  Product     |-----------------------------------------------------------|
|              | Rule editor:                                              |
|              |  Kind [Sum ▾]  Attribute [Balance ▾]                      |
|              |  Children [OrderList → Order ▾]  Summed [AmountTotal ▾]   |
|              |  Where   [ fn: ShippedDate is empty            ] (FB)     |
|              |                                     [Cancel] [Save Rule]  |
+--------------+-----------------------------------------------------------+
```

- **Pick, don't type:** entities, attributes and child/parent roles come from the model
  (pop-ups); only formula / constraint / where bodies are typed, as FB.
- **FB editor** for bodies, with the row-access calls offered as snippets
  (`LogicDouble( row, @"…" )` for each attribute) and dependencies shown as they are
  detected.
- **Validation in the Studio:** unknown attributes, type mismatches (sum of a text
  column), formula cycles — before anything is generated. Optionally run `fblint` on the
  generated rule file.
- **Saved** in the project as `Rules.json` (the source of truth, next to `Design.json`);
  **generated** into `FBapp/<Entity> Rules.incl` + `Logic Rules.incl` (includes them, in the
  project's Rules group) by *Generate App* / a new *Generate Rules* command.
- **Explain:** for a selected attribute, show the chain that maintains it
  (`Customer.Balance ← sum Order.AmountTotal ← sum OrderDetail.Amount ← Quantity * UnitPrice`).
- **Later:** a test bench — enter a change against the project's database copy and see the
  logic log and resulting values, rolled back afterwards.

## 4. Licensing — read before writing code

LogicBank's `LICENSE` file is **Apache 2.0 with the "Commons Clause"**, which withholds the
right to *Sell* — to offer, for a fee, a product or service whose value derives
substantially from the software (consulting and hosting included). Its `setup.py` and
`pyproject.toml` say **BSD**. The two disagree.

- This design describes *behaviour* (rule semantics, the order of operations, the
  adjustment idea), which is not copyrightable; the FB engine will be **our own code**,
  written from this document, **not a line-by-line translation** of `logic_row.py` etc.
- Even so, a commercial Imagery product built on LogicBank's design is close to what the
  Commons Clause is about. **Recommendation: ask Val Huber** — for written permission or
  for clarity on which license applies (and a nod in the credits either way). Until then,
  keep this clean-room: read LogicBank's docs and tests for semantics, not its code for
  structure.
- LogicBank Studio: check its license separately before borrowing any UI or ideas from it
  beyond what is public.

## 5. Plan

1. **Engine core** — rule bank, LogicRow, insert/update/delete sequence, formulas with
   explicit dependencies and pruning, constraints, transaction + rollback. Test app:
   Northwind's `OrderDetail.Amount`.
2. **Aggregates** — sum/count with where, delta adjustment, re-parenting, one write per
   role, chaining (`Order.AmountTotal` → `Customer.Balance` → credit constraint).
3. **Copy, parent check, cascade** (delete / nullify / prevent), events.
4. **Studio** — Rules page, `Rules.json`, rule generation, validation, Explain.
5. **ALS import** of `declare_logic.py`; test bench; allocate / copy-children extensions.
**Acceptance tests (behaviour, not code):** LogicBank's repository has about 30 example
scenarios under `examples/` (`sum_dequalify`, `sum_null_values`, `multi_relns`,
`insert_parent`, `cascade_delete_multi_parent`, `referential_integrity`,
`payment_allocation`, `copy_children`, `concurrent_adjust`, …) and a Northwind test suite
(`examples/nw/tests`: add order, ship order, change an order's customer, delete customer,
…). Each becomes an FB test against the project's SQLite copy, with the expected values
taken from the scenario's description, written by us.

6. A Python reference (`tools/logic_reference.py`) running the same rules on the same
   SQLite file, to check the FB engine's results — the way `sqlite_model.py` checks the
   model reader.
